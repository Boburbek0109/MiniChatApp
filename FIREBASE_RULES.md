# Правила Firebase: текущий этап

Файлы `firestore.rules` и `storage.rules` — согласованный вариант для текущих
личных чатов. Создание файлов не публикует правила в Firebase. Для публикации
нужно скопировать каждый файл в Rules соответствующего продукта.

## Проверки перед завершением этапа

Новый комплект проверен чтением Swift-кода и документации, но не выполнялся в
Firestore Emulator: в доступном окружении отсутствует Java Runtime.
Результаты предыдущих проверок не считаются автоматическим тестом нового файла.

- Регистрация, поиск пользователей, сохранение своего профиля работают.
- Первый отправитель создаёт чат и сообщение одной batch-операцией.
- Второй участник отвечает; первый снова отвечает, без ошибки permissions.
- Существующие чаты читаются; отметка прочтения не вызывает ошибку permissions.
- Постороннему UID запрещены чтение и запись сообщений чужого чата.
- Запрещены замена участника, создание чата с одним/повторяющимся/третьим UID.
- Запрещены подмена senderId, receiverId, senderEmail и chatId сообщения,
  пустой текст, произвольная дата, лишние поля и редактирование сообщения.
- Автор-участник может удалить своё сообщение; другой участник — нет.
- Удаление документа чата клиентом запрещено до реализации корректной очистки.
- Для аватара: свой JPEG 100000 байт разрешён; чужой путь, JPEG 6291456 байт,
  text/plain и запись без авторизации запрещены. Свой файл можно удалить.

Проверки запретов делаются симуляцией или в эмуляторе, не порчей реальных данных.
Для проверки первого сообщения требуется именно batch; отдельная симуляция
создания сообщения без родительского чата не проверяет этот сценарий.

## Изменения относительно последних правил из переписки

- Собраны ранее согласованные проверки участников, сообщений и аватаров.
- Добавлены соответствие uid профиля ID документа, соответствие ID чата его
  участникам при создании и запрет менять поле id чата на другое значение.
- У сообщения проверяются набор полей и email отправителя из auth-токена.
  После смены email может понадобиться обновление токена/повторный вход.
- Создание и удаление чата теперь не симметричны: удаление отключено, поскольку
  оно отсутствует в интерфейсе и не удаляет автоматически подколлекцию messages.

## Не закрытые этим этапом вопросы

Это не завершённый аудит безопасности и не основание считать весь пункт №5 готовым.

- В users смешаны публичные и личные поля. Авторизованные пользователи по-прежнему
  могут читать чужие email и birthDate. Нужны изменение схемы и Swift-кода (пункт №6).
- participants защищены, но lastMessage, lastSenderId, updatedAt и unreadCounts
  не привязаны правилами к конкретной записи сообщения. Для строгой проверки
  потребуется согласовать схему/операции клиента или доверенный сервер.
- В ChatService setData использует ключи unreadCounts с точками, а markChatAsRead
  использует updateData с путями полей. Семантику и хранение счётчиков нужно
  отдельно проверить; эти правила не объявляют их защищёнными от подмены.
- Разрешение удаления своего сообщения не обновляет сводку чата автоматически.
- До создания родительского чата подписка на messages может получать отказ.
  Восстановление после собственной отправки не покрывает все гонки и случаи,
  когда первое сообщение отправляет другой участник.
- Временный null в createdAt при ожидании serverTimestamp остаётся отложенной
  проблемой декодирования; правила записи её не исправляют.
- Storage проверяет заявленный MIME-тип, а не содержимое JPEG. Доступ по download
  URL с токеном также требует отдельного рассмотрения при требованиях приватности.
- Ограничение длины текста, защита от массовых запросов и проверка существования
  аккаунта получателя этим этапом не вводились.

После проверки этого комплекта можно вернуться к пункту №1 (безопасная загрузка
профиля), сохранив перечисленные вопросы открытыми в списке работ.
